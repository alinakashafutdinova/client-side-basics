## Цель

В этой работе я изучила три причины утечек памяти при работе с DOM: забытые обработчики событий, ссылки в глобальной коллекции и работающие таймеры. Для каждого случая сделала пример, посмотрела, какие объекты остаются в памяти после удаления со страницы, и добавила исправление.

## Как проводила эксперимент

Для сравнения использовала Chromium и метод трёх снимков. Каждый сценарий проверяла отдельно:

1. Перед началом вызвала сборку мусора и сняла снимок №1 — исходное состояние.
2. Создала 80 карточек и удалила их из DOM, не убирая удерживающие ссылки. Повторно вызвала сборку мусора, сняла снимок №2.
3. Повторила создание и удаление ещё 80 карточек, вызвала сборку мусора и сняла снимок №3.
4. Нажала «Устранить утечку», снова вызвала сборку мусора и проверила результат.

Для автоматизированной проверки использовала интерфейс Chrome DevTools Protocol: `HeapProfiler.collectGarbage`, `HeapProfiler.takeHeapSnapshot` и `Runtime.getHeapUsage`. В тестовой среде браузер не разрешает переход на локальные URL, поэтому тест загрузил **тот же HTML, CSS и JavaScript** напрямую в браузер. Числа ниже получены из реальных снимков памяти Chromium, но не являются замерами моего MacBook.

## Эксперимент 1. Забытые обработчики событий

**Что сделала.** Для каждой карточки добавила обработчик `resize` на `window`. В функции-обработчике используется сама карточка. После удаления карточек из контейнера обработчики намеренно не снимаются. Повторила это дважды.

**Что увидела.** На странице карточек уже нет, а в снимках остаются отсоединённые элементы. Их количество увеличилось с 1 520 до 3 040.

**Причина.** Цепочка удержания: `window` → обработчик события `resize` → функция `onResize` → переменная `card` в замыкании → удалённый DOM-элемент. Дополнительная ссылка на эту же функцию хранится в массиве `state.listeners`, чтобы позже можно было её снять. Обе связи нужно очистить, иначе карточка останется в памяти.

**Как исправила.** Вызвала `window.removeEventListener('resize', listener)` для каждой функции, а затем очистила массив `state.listeners`. После исправления отсоединённых узлов в тестовом снимке не осталось.

## Эксперимент 2. Ссылки на узлы в глобальном Map

**Что сделала.** Создавала карточки и записывала их в `window.memoryLabCache` через `Map.set`. После очистки DOM коллекцию не трогала.

**Что увидела.** В Map после первого цикла оставалось 80 записей, после второго — 160. В снимке при этом увеличивалось количество отсоединённых DOM-узлов.

**Причина.** Цепочка удержания: `window` → `memoryLabCache` → записи `Map` → удалённая карточка. Удаление элемента со страницы не очищает коллекцию, в которой хранится ссылка на этот элемент.

**Как исправила.** Вызвала `window.memoryLabCache.clear()`. Для настоящего приложения можно удалять отдельные записи через `Map.delete`, когда элемент больше не используется.

## Эксперимент 3. Замыкания и таймеры

**Что сделала.** Для каждой карточки запустила `setInterval`. Функция внутри интервала использует переменную `card`. Когда карточки удаляются со страницы, интервалы намеренно продолжают работать.

**Что увидела.** После двух циклов работало 160 таймеров. Отсоединённых узлов в снимках тоже становилось больше.

**Причина.** Цепочка удержания: система таймеров браузера → функция `updateDetachedCard` → переменная `card` в замыкании → удалённый DOM-элемент. Пока работает таймер, ссылка на карточку остаётся достижимой.

**Как исправила.** Сохранила идентификаторы интервалов и при очистке вызвала `clearInterval` для каждого. После этого отсоединённые узлы перестали удерживаться.

## Вывод

Удаление элемента из DOM само по себе не гарантирует освобождение памяти. Если другая часть программы продолжает ссылаться на него, сборщик мусора не сможет удалить этот объект. В трёх проверенных сценариях удерживающими ссылками были обработчики `window`, глобальный `Map` и активные интервалы. После устранения этих ссылок отсоединённые DOM-узлы исчезли из тестовых снимков. На практике важно не забывать удалять глобальные обработчики, очищать кэши и останавливать таймеры.

Числа JS-кучи зависят от версии браузера и окружения, поэтому их нельзя напрямую сравнивать с показателями другого компьютера. Также размер JSON-файла снимка кучи не равен объёму памяти JavaScript. Главные признаки утечки здесь — повторяемое накопление недостижимых для страницы, но удерживаемых по ссылкам DOM-узлов и их освобождение после исправления.
